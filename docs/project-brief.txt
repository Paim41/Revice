# 1. PRODUCT OVERVIEW

Revice is a cross-device monitoring ecosystem.

The user's primary device is a **POCO F7 Android smartphone**. It acts as the main dashboard for monitoring multiple Android phones and Windows computers.

Additional Android devices and Windows computers run lightweight monitoring agents that collect and securely synchronize their system status.

The main Android dashboard displays the latest available information for all connected devices.

### Supported platforms

1. Android smartphones and tablets.
2. Windows 10/11 desktops and laptops.

iOS is explicitly excluded from version 1.0.

### Core monitoring features

- Battery percentage.
- Battery charging status.
- Battery temperature when supported.
- Battery health status when supported.
- Battery voltage when supported.
- Battery cycle count when supported.
- Total storage.
- Available storage.
- Used storage.
- Storage usage percentage.
- Device information.
- Monitoring timestamps.
- Historical battery and storage analytics.
- Windows CPU usage.
- Windows RAM usage.
- Windows drive information.
- Windows uptime and power status.
- Low-battery alerts.
- Storage warnings.
- Device monitoring status.
- Telegram notifications.

### Product principles

- One Android APK supports unlimited devices in application design, subject to backend quotas.
- One Windows application supports multiple independent PCs.
- All devices belong to an authenticated owner.
- A device must be explicitly paired before it can publish monitoring data.
- The user can rename, group, inspect, and revoke devices.
- Never display fabricated health metrics.
- Never confuse stale information with real-time information.
- Prioritize security, reliability, battery efficiency, and understandable UX.
- Prefer an offline-first monitoring approach wherever appropriate.

# 9. SECURITY REQUIREMENTS

Security is mandatory.

Implement the following controls.

### Firebase Authentication

Use Firebase Authentication for owner accounts.

Require authenticated ownership checks.

Protect all device records and monitoring data from cross-account access.

### Firebase Security Rules

Default deny.

Permit owners to read their own approved data.

Only expose the minimum required data.

Disallow direct client writes to privileged monitoring records when the Worker is responsible for those writes.

Protect all private credential and pairing paths.

Test rules using Firebase Emulator.

### Cloudflare authorization

The Worker must distinguish between:

1. Authenticated owner requests.
2. Authenticated agent requests.
3. Verified Telegram webhook requests.

For owner requests, verify Firebase ID token signatures, issuer, audience, expiry, and owner identity using a compatible JWT verification approach.

Never merely decode the JWT and trust its claims.

For agent requests, verify independently issued credentials and device ownership.

### Agent credentials

Generate a cryptographically secure random credential for each device.

- Store only protected credentials on the agent.
- Store credential hashes on the backend.
- Support token revocation and rotation.
- Use constant-time comparison where appropriate.
- Never share a single universal agent token across devices.

### Android storage

Use Android Keystore-backed secure storage for sensitive agent credentials where supported.

### Windows storage

Use Windows DPAPI or equivalent OS-level credential protection.

Do not store plaintext secrets in configuration files.

### Service account credentials

Use Cloudflare Worker secrets.

For privileged Firebase REST requests, use properly scoped Google OAuth2 access tokens obtained using a securely stored service account credential.

Do not assume Firebase Admin SDK works unchanged inside Cloudflare Workers.

Verify the chosen approach is compatible with the deployed Workers runtime.

### Telegram secrets

Telegram bot token must exist only on the server.

Never include it in Android or Windows binaries.

### Other security controls

- HTTPS only.
- Input validation.
- Request size limits.
- Rate limiting with persistent state.
- Replay protection.
- Idempotency keys.
- Secure logging.
- Secret redaction.
- Credential revocation.
- Clear authorization errors.
- No publicly writable Firebase rules.
- No unrestricted administrative endpoints.
- No embedded service account credentials.
- No unsafe automatic fallback when authentication fails.

Do not rely on client-side UI checks for security.

# 10. SECURE DEVICE PAIRING

Provide an intuitive pairing system.

### Pairing flow

1. The owner opens Revice on POCO F7.
2. The owner selects Add Device.
3. The backend creates a temporary pairing session.
4. Revice displays a QR code or six-digit pairing code.
5. The secondary Android or Windows Agent submits the pairing request.
6. The owner reviews the requesting device.
7. The owner selects Approve or Reject.
8. Upon approval, the backend registers the device and issues its individual credential.
9. The agent securely stores the credential.
10. The device sends its first telemetry report.

### Requirements

- Five-minute pairing expiry.
- One-time code usage.
- Cryptographically random codes.
- Limited pairing attempts.
- Explicit owner approval.
- No auto-approval.
- No sensitive credentials displayed in logs.
- Ability to cancel.
- Ability to revoke later.
- Duplicate device handling.
- Safe handling when pairing is interrupted.

Use atomic operations or suitable concurrency controls where needed so two simultaneous requests cannot consume the same pairing session.

### Local POCO registration

The owner's own Android phone must also register as a monitored device.

Provide a secure first-device enrollment flow.

Avoid requiring users to scan a QR code displayed on the same phone.

# 13. DEVICE CONNECTION STATUS

Do not use fake online detection.

Design clear monitoring states:

### Live

A connection or fresh active reporting state is actually confirmed.

### Recent

Recent telemetry has been received within the expected reporting window.

### Stale

The device has not reported within its configured expected interval and grace period.

### Offline

A confirmed connection was lost, or the system has sufficient evidence to classify the device as disconnected.

### Never Synced

The device has been paired but has not successfully reported telemetry.

Use accurate timestamps.

Android Doze may delay monitoring, so avoid treating a delayed Android reading as proof the phone has shut down.

Store sufficient information to explain the status to the user.

# 17. DEVELOPMENT QUALITY & ANTI-SLOP RULES

Follow strict code quality standards inspired by professional anti-slop development practices.

### Architecture

- Clear module boundaries.
- Separation of UI and business logic.
- Separation of repositories and services.
- Reusable components.
- Centralized configuration.
- Typed data models.
- Explicit interfaces where useful.
- Minimal coupling.
- Simple, testable functions.

### Code quality

- No duplicate implementations.
- No unnecessary abstraction.
- No dead code.
- No excessive dependencies.
- No meaningless wrappers.
- No giant all-in-one files.
- No unused imports.
- No hardcoded secrets.
- No unnecessary global mutable state.
- No broad catch blocks that silently suppress errors.
- No fake success messages.
- No unfinished functions presented as implemented.
- No invented API behavior.

### UI quality

- No inconsistent padding.
- No random colors.
- No decorative effects without purpose.
- No inaccessible contrast.
- No irrelevant icons.
- No excessive animations.
- No crowded metric cards.
- No fake statistics in production.

### Reliability

- Handle null values.
- Handle unsupported metrics.
- Handle API failures.
- Handle lost network connectivity.
- Handle expired tokens.
- Handle revoked devices.
- Handle device sleep.
- Handle Android battery restrictions.
- Handle app restart.
- Handle invalid timestamps.
- Handle duplicate requests.

### Documentation

Document important decisions.

Avoid comments that merely repeat the code.

Explain non-obvious security and platform behaviors.

### Dependencies

Prefer maintained packages with compatible licenses.

Use current stable versions verified for the target toolchain.

Pin appropriate versions and generate reproducible dependency lockfiles.

Do not blindly use outdated example code.

# 18. ENVIRONMENT CONFIGURATION

Create safe template configuration files.

Example non-secret configuration:

    FIREBASE_PROJECT_ID=
    FIREBASE_DATABASE_URL=
    FIREBASE_ANDROID_APP_ID=
    CLOUDFLARE_GATEWAY_URL=

Example Worker secrets:

    FIREBASE_SERVICE_ACCOUNT_JSON=
    TELEGRAM_BOT_TOKEN=
    TELEGRAM_WEBHOOK_SECRET=
    AGENT_TOKEN_HASH_KEY=

Use only the secrets actually required by the final implementation.

Document the difference between Firebase public client configuration and privileged server credentials.

Provide:

- `.env.example` or equivalent.
- `.dev.vars.example` for Workers.
- `.gitignore` exclusions.
- Setup instructions.
- Secret rotation instructions.

Never commit real secrets.

Do not ask me to paste private keys into public source code.

# 21. USER SETUP EXPERIENCE

The final experience must be straightforward.

### Android installation

The user should:

1. Install `Revice.apk`.
2. Open Revice.
3. Sign in.
4. Register their POCO F7.
5. See actual local battery/storage.
6. Add another Android using pairing.
7. View both devices from the dashboard.

### Windows installation

The user should:

1. Run `Revice-Agent-Setup.exe`.
2. Open the installed agent.
3. Enter a pairing code.
4. Approve pairing from the Android dashboard.
5. Choose whether to start with Windows.
6. Minimize the application to the system tray.
7. See the Windows device in the Android dashboard.

### Telegram setup

The user should:

1. Create a Telegram bot using BotFather.
2. Configure its token securely in Cloudflare.
3. Open Revice Settings.
4. Select Link Telegram.
5. Complete secure linking.
6. Send a test notification.
7. Receive future alerts based on real monitoring events.

Write beginner-friendly step-by-step installation documentation.

Use practical Windows PowerShell commands where appropriate.

# 22. COST & PERFORMANCE OPTIMIZATION

This is a personal project intended to start with no recurring infrastructure cost.

Optimize for Firebase Spark and Cloudflare Workers Free.

Use:

- Small telemetry payloads.
- Efficient database paths.
- Scoped realtime listeners.
- Bounded history.
- Aggregated statistics.
- Scheduled cleanup.
- Controlled retry behavior.
- Caching.
- Minimal backend CPU usage.

Do not use expensive real-time polling for all devices.

Do not send full historical data on every synchronization.

Do not introduce billable Firebase features without explicit approval.

If a free-tier quota or limitation blocks a feature, document the issue and provide a safe alternative.

Never bypass security to reduce cost.
